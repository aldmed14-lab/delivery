        order_status            // "placed" | "accepted" | "preparing" | "ready" |"cancelled"
        delivery_status          // "pending" | "assigned" | "arrived_to_store"| "picked_up" | "on_the_way" | "arrived" | "delivered"
        admin_report_id  // the reports/{} doc id, once escalated - set automatically by the courier-search hard cap (find-courier system, no driver after 10 min), OR by the customer's own "Call Admin" button on live_order_page.dart once the order is 30+ min past its estimated window (requestAdminCall Cloud Function) - either way, auto-creates a real report instead of just a dead flag, so it actually surfaces in the admin Reports queue. Never a kill switch on its own
        admin_by
        created_at
        city // denormalized from stores.city the moment the order is accepted (advanceOrderStatus) - find-courier system's candidate query needs an equality field to filter delivery docs by, orders never carried one before this

        search_active // boolean, default true - find-courier system, an ADMIN-ONLY kill switch. Nothing automated ever sets this false, only an explicit admin action - stops the whole search (including rejecting a still-pending accept, not just new offers)
        searching_courier // boolean, default false - find-courier system, purely a display flag: true once the search has actually started (generation 1 claimed), never changes again. Not used for any race-prevention logic itself - search_number's transactional claim is what actually does that
        search_number // int, default 0 - find-courier system, the fencing/generation counter. Every attempt (start, refusal-retry, timeout-retry, scheduled retry) claims the next number via one shared transaction before doing anything; a scheduled Cloud Task carries the number that was current when it was scheduled, and is a stale no-op if that number no longer matches by the time it fires
        start_search_courier // find-courier system: set once, the moment generation 1 is actually claimed (whichever of the two triggers wins). The search's own elapsed-time clock (geohash tier, 2-min tried_delivery_ids reset) counts from this, not accepted_at, and never changes again afterward
        tried_delivery_reset_window // find-courier system, internal bookkeeping only: which 2-minute window tried_delivery_ids was last reset for (an integer), so repeated "no driver found" retries within the same window don't wipe the list every single time
